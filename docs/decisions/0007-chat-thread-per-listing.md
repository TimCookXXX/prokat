# 0007. Переписка: тред на пару «объявление + арендатор», без реального времени

## Status

Accepted (2026-08-31)

Частично отменяет [0005](0005-booking-as-request-no-payments.md), где было
записано, что чата в сервисе нет.

## Context

Сервис сводит людей, но до появления переписки единственным каналом связи была
заявка на бронь: телефоны раскрываются только после подтверждения. Спросить
«а можно посмотреть?» или «свободно на выходных?» до брони было негде.

Развилок было три: чем считать тред, как считать непрочитанное и нужна ли
доставка в реальном времени сразу.

## Decision

**Тред — это пара (объявление, арендатор).** Не пара людей и не переписка
внутри заявки. У владельца с десятком вещей разговоры не смешиваются, а контекст
разговора виден без вопросов. Ключ закреплён `UNIQUE (listing_id,
customer_user_id)`, тред заводится вместе с первым сообщением. С
[0017](0017-thread-as-deal-journal.md) первым сообщением может быть запись о
сделке — тред тогда появляется без участия человека, вместе с заявкой.

**Непрочитанное считается курсором на треде** — `owner_last_read_message_id` и
`customer_last_read_message_id`, по одному на сторону. Не отметка `read_at` на
каждом сообщении. Курсор — ULID, поэтому сравнивается тем же индексом
`(thread_id, id)`, которым листается история, и двигается только вперёд.

**Реального времени нет.** Сообщения доезжают при следующем заходе на сайт.
Ни писем, ни push, ни вебсокетов.

> **Отменено** решением [0009](0009-realtime-as-a-separate-process.md):
> доставка идёт вебсокетом через отдельный процесс. Остальные пункты этого
> документа в силе.

**Отправка идёт через Server Action, а не по отдельному каналу.** Права, zod и
лимиты остаются там же, где у всех остальных мутаций.

## Consequences

**Положительные.** Схема выдерживает добавление доставки в реальном времени без
миграций: транзакция отправки уже одна (вставка сообщения плюс сдвиг
`last_message_at`), Server Action уже возвращает созданное сообщение целиком, а
лента уже живёт клиентским компонентом, засеянным из SSR. Курсорная модель
непрочитанного даёт запись в одну строку на прочтение вместо записи на каждое
сообщение.

**Отрицательные и принятые.**

- **Человек не узнаёт о сообщении, пока не зайдёт сам.** Это главная цена
  решения и главный повод для следующей задачи.
- Список переписок читается двумя запросами (где я владелец и где я арендатор)
  со слиянием в приложении: `WHERE owner = me OR customer = me` не даёт
  использовать ни один из двух индексов.
- Переписка не пишет событий в `events` — отклонение от общего паттерна мутаций,
  принятое ради объёма.
- Модерации переписки нет: ни жалоб, ни просмотра админом. Против спама
  работают только лимиты.

**Что это запрещает.**

- Считать непрочитанное отметкой на сообщении: это потребует миграции с
  пересчётом всей истории и сломает курсорную пагинацию.
- Заводить второй тред на ту же пару в обход `startThread` — уникальный индекс
  такую вставку отвергнет.
- Строить доставку сообщений на `revalidatePath`: страницы переписки
  `force-dynamic`, и собеседнику он ничего не обновит.
- Отправлять сообщения мимо Server Action — иначе проверки прав, валидация и
  лимиты придётся продублировать во втором месте. Уточнение из
  [0017](0017-thread-as-deal-journal.md): записи о сделке пишутся мутациями
  заявки в обход `canPostMessage` и `postMessageSchema` — это не реплика,
  которую кто-то отправил, а факт; репликам людей путь по-прежнему один.
